# 四条实施路线

建议：**先用 A 的方式建立基线，同时实施 C 的 M0/M1；只有职位筛选和材料质量通过验收后，再扩展提交自动化。** 如果只是尽快找到工作且不想维护软件，选择 A 即可。

以下时间是单名熟悉相关技术的开发者的粗略工作日估算，不是交付承诺；月费为个人小规模使用的规划预算，非供应商报价，不含开发时间、税费和商业岗位数据。商业功能证据见 [调研](RESEARCH.md)。

| 路线 | 核心组合 | 达到首个可用闭环的估算 | 月度运行规划预算（USD） | 主要取舍 |
| --- | --- | --- | --- | --- |
| A：直接组合现成工具 | Simplify/Huntr + Teal 或自带 tracker + remote 职位源 | 1–3 天设置与比较 | 0–100 | 上手快；画像/评分和历史记录受产品约束 |
| B：低代码个人助手 | n8n + HTTP/RSS + 规则/LLM + 表格或轻量数据库 + 现成填表扩展 | 4–8 天 | 20–120 | 快速迭代；复杂状态和长表单维护困难 |
| C：自建混合系统（推荐） | TypeScript + SQLite + 公开 API + 材料模板 + Playwright，必要时 Stagehand | 10–20 天 | 20–150 | 可解释、可控；需要维护来源与 ATS 适配器 |
| D：产品化自动申请平台 | Web 控制台 + Postgres + 持久化任务队列 + 浏览器 worker + 用户隔离 | 40–80 天以上 | 150–1,000+ | 可服务多人；数据许可、隔离、运营和成本显著增加 |

预算假设：C 每月处理约 1,000–3,000 条原始职位、100–300 份材料草稿、一个本地浏览器，不代表存在这么多合格职位，也不是投递配额。D 的预算仅代表很小规模试点，不能据此估算生产服务。

## A：买能力，验证求职流程

步骤：补齐真实资料与筛选条件；选择一个填表工具，避免多个扩展同时修改表单；从目标来源筛出 30–50 个岗位；选择 10–20 个合适岗位完成材料与填表对照；用户决定实际提交。

保留自己的主档案、简历版本与申请台账。若比较托管自动申请产品，先确认能导出记录、排除重复公司、表达所在地要求并限制提交范围。

退出条件：候选质量和人工时间符合需求就继续使用；如果主要痛点是地区筛选失误、历史数据不透明或无法控制材料，再进入 C。不要同时让多个服务申请同一批岗位。

## B：低代码流水线

流程：定时获取 RSS/API → 标准化 → 数据库去重 → 硬性过滤 → LLM 摘要/排序 → 每日审核清单 → 现成扩展或人工申请 → 更新记录。

首版只编排采集、摘要和提醒。提交仍走已验证表单工具，不把一个 HTTP 节点误当所有 ATS 的提交能力。以稳定 job key 存状态，不用工作流运行编号代替申请身份。

适合已有 n8n 经验、主要想减少找岗位时间的用户。若必须处理原子去重、版本绑定、断点恢复和很多网站适配，迁移 C；向外提供产品前再核查 n8n 许可及数据来源用途。

## C：本地混合系统

第一阶段只做两个来源适配器：Himalayas + Greenhouse 企业清单；Lever/Ashby 为下一批。手动 URL 导入一直保留。

核心差异化能力：

- 按所在地、授权、时区和雇佣类型进行证据驱动的三态判断。
- 每段简历陈述指向用户确认的事实，保留原版和改写差异。
- 为特定 ATS 建确定性适配器，AI 只处理未知字段的解释/映射；不拥有任意工具权限。
- 将生成草稿、上传/填写和提交分成不同模式，后两者明确涉及向招聘网站提供资料。
- 统一记录跨来源重复、提交回执、人工修正和面试结果。

首个 ATS 的最终选择以实际目标岗位样本为准，暂以 Greenhouse 为候选。先有可靠的筛选队列和材料包，再做可视化界面与更多站点。

成熟后的自动提交可按允许的域名/ATS、明确资格、用户确认答案库、材料版本、每日上限和有效期限定。已有批量授权不必每份重复确认；超出范围的申请进入审核队列。

## D：面向多人产品化

在 C 的闭环验证后增加：租户隔离、浏览器会话隔离、密钥管理、任务租约/并发锁、费用分摊、授权撤销、删除/导出、故障告警与人工接管。

基础产品定位可选“跨境 remote 资格筛选与申请助手”，优先服务一个岗位群体和国家组合。不要一开始承诺所有国家、所有 ATS 的无人值守投递。

进入条件：个人版至少有一轮成熟申请反馈；有明确的外部试用需求；证明每份申请变动成本和支持成本可控；岗位数据与软件许可覆盖实际产品用途。

## 成本怎么算

`月成本 = 模型输入输出费用 + 浏览器运行时长费用 + 存储/数据库 + 数据源费用 + 订阅费用`。

工程时间另算：`实际总投入 = 上述费用 + 开发/维护小时 × 自己的小时机会成本`。先用 20 份材料记录 token、耗时、失败重试，再代入实际供应商当日报价。缓存 JD 抽取结果；硬规则淘汰的岗位不进入材料生成；设置月度硬上限。

## 首轮对照实验

用相同画像、相近职位类型和同一评分标准比较 A 与 C 的材料/填表阶段；同一个职位只通过一个渠道实际申请。记录中位人工耗时、修正字段数、事实错误数和回执情况。面试反馈按投递周分组，至少等待 21 天再讨论转化，不能把不同时段/不同岗位难度的差异全归因于工具。
